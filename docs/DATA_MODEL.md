# 데이터 모델 v0

현재 구현과 기존 JSONL을 연결하는 규칙이다. 모든 데이터 파일은 BOM 없는 UTF-8과 LF 줄바꿈을 사용하고 마지막에 줄바꿈을 둔다. 세 JSONL 파일은 한 줄에 JSON 객체 하나를 기록하며, 콜론과 쉼표 뒤에 공백 하나를 둔다. 빈 줄은 허용하지만 주석, 알 수 없는 필드, 한 줄에 여러 객체는 오류다. 한 줄 크기 제한은 1 MiB다. 세 파일은 모두 존재하고 최소 하나의 레코드를 포함해야 한다. `practice.json`은 공백 두 칸 들여쓰기로 정리한다.

## 음 그룹 — `meta.jsonl`

```json
{"type": "meta", "id": "ga", "sound_ko": "가", "sound_en": "ga"}
```

- `type`은 `meta`, `id`는 소문자 영문으로 된 고유 키다.
- `sound_ko`, `sound_en`은 필수 문자열이다.
- 로마자 표기는 기존 값을 보존한다. 특정 로마자 표기법에 대한 적합성은 아직 검증하지 않는다.

## 한자 독음 — `character.jsonl`

```json
{"type": "character", "id": "ga-005", "hanja": "家", "meaning_ko": ["집", "가족"], "meaning_en": ["house", "family"]}
```

- `type`은 `character`, `id`는 `<meta ID>-<3자리 이상 숫자>` 형식의 고유 키다.
- 접두어는 존재하는 음 그룹을 참조해야 한다.
- 기존 번호 규칙: `000~099` 중등, `100~199` 고등, `200~` 확장. 프로그램은 ID 형식과 음 그룹 참조를 검증하며 교육과정 분류 자체는 검증하지 않는다.
- `hanja`는 공백이 아닌 유니코드 문자 하나, 두 의미 필드는 비어 있지 않은 문자열 배열이다. 한자 부호 영역에 속하는지 또는 실제 훈음이 맞는지는 별도의 내용 검수 대상이다.
- 같은 글자의 서로 다른 독음 레코드를 허용한다. 같은 글자와 같은 음 그룹의 중복은 오류다.
- ID는 참조를 위해 보존한다. 번호를 다시 매기거나 표기를 바꾸는 작업은 별도 이관 규칙이 필요하다.

## 단어 — `normal_word.jsonl`

```json
{"level": "normal", "word": "가격", "hanja": "價格", "meaning_ko": "물건의 값", "meaning_en": "price", "components": ["價", "格"]}
```

- `level`, `word`, `hanja`, `meaning_ko`, `meaning_en`은 필수 문자열이다. `level`의 허용 값 목록이나 TOPIK 등급 매핑은 아직 정하지 않았다.
- `components`는 두 개 이상의 한자 표기를 순서대로 가진다. 각 글자는 한자 파일에 있어야 하고, 이어 붙인 결과는 `hanja`와 같아야 한다.
- `semantic_hint`는 선택 문자열이다. 실제 뜻과 구성 풀이를 구분하며, 복잡한 어원을 프로그램이 임의로 생성하지 않는다.
- 현재 단어 키는 `(word, hanja)` 쌍이다. 같은 한글 표기라도 한자가 다르면 별도 항목이다.
- 같은 `(word, hanja)`의 다의어는 현재 한 항목의 풀이로 취급한다. 뜻별 ID와 예문·출처·검수 상태는 다음 스키마 작업에서 설계한다.

## 그래프와 조회

단어 노드는 `(word, hanja)`, 한자 노드는 글자 자체로 구분하는 이분 그래프다. 읽기와 의미는 한자 노드에 연결되는 독음 레코드로 유지한다.

- 단어 조회: 한글 단어 또는 한자 표기와 정확히 일치하는 모든 항목을 반환한다.
- 한자 조회: 글자, 한자 ID 또는 한글 음과 일치하는 독음 레코드 및 연결 단어를 반환한다.
- 한 단어의 같은 글자가 반복되면 분해 결과에는 모든 위치를 보존하고, 역색인에는 해당 단어를 한 번만 연결한다.
- 하나의 글자에 여러 독음이 있으면 분해 결과에 후보를 모두 제공한다. 한글 음절만으로 어떤 독음인지 선택하거나 두음법칙을 추정하지 않는다. 독음별 조회에서도 연결 단어는 글자 기준으로 공유된다.
- 입력 파일의 순서를 유지해 결과가 재현되도록 한다. 빈 조회 결과는 JSON `[]`다.
- 정확 일치 조회는 유니코드 원문을 그대로 비교한다. 웹 검색은 표기·뜻·음·ID의 부분 문자열 검색을 별도로 지원한다. 이체자·호환 한자·두음법칙에 따른 검색 별칭은 아직 지원하지 않는다.

로딩 시 ID 중복, 필수 필드, 한자·음 참조, 구성 순서를 검사한다. 오류는 파일명과 실제 줄 번호를 포함하고, 잘못된 일부 데이터만으로 그래프를 반환하지 않는다. 검증 성공은 언어적 정확성이나 학습 효과를 보증하지 않는다.

## 문맥 연습 — `practice.json`

웹 앱 전용 JSON 객체다. CLI의 세 JSONL 파일과 독립적으로 검증한다.

- `version: 1`, `source`, `review_status: "draft"`, 비어 있지 않은 `questions` 배열을 기록한다. 현재 작성 예문은 검수 전 초안이다.
- 문항은 고유 `id`, `prompt_ko`, `prompt_en`, `explanation_ko`, `explanation_en`, `answer`, `options`를 가진다.
- 한국어·영어 해설에서 한자를 직접 쓰면 매번 글자 바로 뒤에 한글 독음을 대괄호로 병기한다. 예: `假[가]는 ‘거짓·가짜’, 名[명]은 ‘이름’과 관련돼요.` 같은 글자가 반복되어도 생략하지 않으며, 여러 독음이 있는 글자는 해당 문맥의 독음을 확인한다. 정답·선택지의 `hanja`는 조회용 원문 표기를 유지한다.
- `answer`와 `options`의 각 항목은 `{ "word": "가명", "hanja": "假名" }` 형태로 기존 단어를 참조한다. 선택지는 서로 다른 2~4개이며 정답이 그중 하나여야 한다.
- 출처·문항 텍스트·중복 ID·단어 참조·선택지·정답을 서버 시작 시 검사한다. 언어적 정확성은 별도 검수가 필요하다.
- 예문은 프로젝트에서 직접 작성했다. 웹 API는 정답과 해설도 제공하며 브라우저에서 학습용으로 채점한다.
