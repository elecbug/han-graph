# 데이터 모델

[프로젝트 소개](../README.md) · [프로젝트 현황](README.md) · [웹 앱 사용 안내](WEB_APP.md) · [개발 안내](DEVELOPMENT.md) · [데이터 작성·검수 원칙](DATA_GUIDELINES.md)

현재 저장 형식과 프로그램의 검증·조회 규칙을 정리한다. 수집 범위와 내용 작성·검수는 [데이터 작성·검수 원칙](DATA_GUIDELINES.md)을 따른다. 어휘 수집 위치, 개별 표기 수정과 대조 출처는 [데이터 작업 기록](../log/UPDATE_LOG.md)에서 관리한다.

## 파일과 작성 형식

| 파일 | 역할 | 읽는 기능 |
| --- | --- | --- |
| `meta.jsonl` | 독음을 묶는 음 그룹 | 모든 CLI 명령과 웹 서버 |
| `character.jsonl` | 한자 글자별 독음·뜻 | 모든 CLI 명령과 웹 서버 |
| `normal_word.jsonl` | 한자어·혼합어·한자 없는 단어의 뜻과 구성 | 모든 CLI 명령과 웹 서버 |
| `practice.json` | 문맥 연습 문항과 해설 | 웹 서버 |

세 JSONL 파일은 모두 존재하고 각각 최소 한 개의 레코드를 포함해야 한다. 작성할 때는 다음 형식을 유지한다.

- BOM 없는 UTF-8, LF 줄바꿈, 파일 끝 줄바꿈
- JSONL은 한 줄에 객체 하나, 콜론과 쉼표 뒤에 공백 하나
- `practice.json`은 하나의 JSON 객체, 공백 두 칸 들여쓰기

로더는 JSONL의 빈 줄을 건너뛰고, 알 수 없는 필드·주석·한 줄의 여러 객체·잘못된 UTF-8을 거부한다. 줄 읽기 버퍼의 상한은 1 MiB다. 공백 폭·LF 사용·마지막 줄바꿈 같은 작성 형식을 모두 검사하는 것은 아니므로 편집 시 유지해야 한다.

## 음 그룹: `meta.jsonl`

```json
{"type": "meta", "id": "ga", "sound_ko": "가", "sound_en": "ga"}
```

| 필드 | 규칙 |
| --- | --- |
| `type` | `meta` |
| `id` | 소문자 영문으로 된 고유 키 |
| `sound_ko` | 비어 있지 않은 한국어 독음 문자열 |
| `sound_en` | 비어 있지 않은 로마자 독음 문자열 |

로마자 표기는 기존 값을 보존한다. 특정 로마자 표기법에 맞는지는 별도 내용 검수 대상이다.

## 한자 독음: `character.jsonl`

```json
{"type": "character", "id": "ga-005", "hanja": "家", "meaning_ko": ["집", "가족"], "meaning_en": ["house", "family"]}
```

| 필드 | 규칙 |
| --- | --- |
| `type` | `character` |
| `id` | `<meta ID>-<3자리 이상 숫자>` 형식의 고유 키; 접두어는 기존 음 그룹 참조 |
| `hanja` | 공백이 아닌 유니코드 문자 하나 |
| `meaning_ko` | 비어 있지 않은 한국어 뜻 문자열 배열 |
| `meaning_en` | 비어 있지 않은 영어 뜻 문자열 배열 |

배열의 각 뜻도 비어 있지 않아야 한다. 기존 ID 번호는 `000–099` 중등, `100–199` 고등, `200` 이상 확장으로 사용한다. 프로그램은 ID 형식과 음 그룹 참조를 검사하며 교육과정 분류 자체는 검사하지 않는다.

같은 글자의 서로 다른 독음은 별도 레코드로 저장할 수 있다. 같은 글자·음 그룹의 중복은 오류다. 한자 부호 영역에 속하는지와 실제 훈음이 맞는지는 별도 검수한다. 기존 ID를 다시 매기거나 글자를 바꿀 때는 참조 이관 규칙이 필요하다.

## 단어: `normal_word.jsonl`

```json
{"level": "normal", "word": "가격", "hanja": "價格", "meaning_ko": "물건의 값", "meaning_en": "price", "components": ["價", "格"]}
```

| 필드 | 규칙 |
| --- | --- |
| `level` | 비어 있지 않은 문자열; 현재 데이터는 `normal`(일반 어휘), `classical`(고전·문어 어휘) 사용 |
| `word` | 비어 있지 않은 한글 표기 문자열 |
| `hanja` | 한자 또는 한글이 섞인 표기 문자열; 한자 구성을 제공하지 않는 항목은 빈 문자열 |
| `meaning_ko` | 비어 있지 않은 한국어 뜻 문자열 |
| `meaning_en` | 비어 있지 않은 영어 뜻 문자열 |
| `components` | 등록된 한자만 원래 순서로 담은 배열; 한 글자도 허용하며 한자 없는 항목은 `[]` |
| `semantic_hint` | 선택 문자열; 구성 한자의 뜻과 단어의 의미를 설명 |

한자어는 `江`처럼 한 글자도 수록한다. 혼합어 `검은색`은 `hanja: "검은色"`, `components: ["色"]`로 저장한다. 기초 어휘의 한자 어근 뒤에 붙은 `-하다`는 제거하고 같은 `(word, hanja)` 항목이 있으면 합친다. 혼합 표기의 한글 부분은 원래 단어의 같은 위치와 일치해야 하며 한자로 등록하거나 그래프에 연결하지 않는다. 파일 형식은 한자 없는 항목의 `hanja: ""`, `components: []`도 지원하지만, 현재 기초 어휘의 수록 정책에서는 이러한 항목을 제외한다. 한자가 있는 표기는 실제 한자 성분을 하나 이상 포함해야 하고, 구성 배열은 그 한자들만 이어 붙인 결과와 같아야 한다. `null`이거나 생략된 구성 배열은 허용하지 않는다.

단어 키는 **`(word, hanja)` 쌍**이다. 같은 쌍의 중복은 오류이며, 한글 표기가 같아도 한자가 다르거나 한자가 같아도 한글 표기가 다르면 별도 항목이다. 같은 쌍 안의 여러 뜻은 현재 하나의 풀이에 담는다. 한자 없는 동형어도 같은 한글·빈 한자 쌍이면 뜻과 용법을 합친다. 외부 목록의 품사·동형어 번호별 대응은 [기초 어휘 수록 기준](BASIC_VOCABULARY.md)을 따른다.

`level`은 학습용 어휘 분류이며 난이도나 TOPIK 등급을 뜻하지 않는다. 현재 저장소는 다음 기준을 사용한다.

- `normal`: 현대의 일반 어휘, 전문 용어, 현재도 통용되는 격식 표현과 성어. 고전·역사를 설명하는 단어라는 이유만으로 분류를 바꾸지 않는다. 예: 고전, 한문, 기하, 비분강개.
- `classical`: 한문 구절·성구, 옛 호칭·관직·제도 용어, 고전이나 문어 맥락을 중심으로 학습하는 어휘. 예: 불역열호, 내손, 하위, 짐량, 포류지질.

뜻풀이와 힌트의 사용 맥락을 검토해 `(word, hanja)`별로 분류한다. 설명에 ‘고전’, ‘문어’가 있는지만으로 자동 판정하지 않는다. 예를 들어 흡연(吸[흡]煙[연])은 `normal`, 흡연(恰[흡]然[연])은 `classical`이다. 한 항목에 현대적 의미와 문어적 의미가 함께 수록되어 있으면 현대적 용법도 고려한다.

기존 로딩 경로를 유지하기 위해 두 분류 모두 `normal_word.jsonl`에 저장한다. 검색·그래프·연습은 기본적으로 두 분류를 모두 사용하며, 사용자가 어휘 필터를 선택하면 해당 분류로 범위를 제한한다. 로더는 `level`이 비어 있지 않은지만 검사하고, 분류의 적절성이나 한글 표기·독음의 언어적 정확성은 별도 검수한다.

### 뜻풀이와 힌트 작성

한국어·영어 설명에서 한자를 직접 쓰면 매번 글자 뒤에 해당 문맥의 한글 독음을 붙인다. 예: `假[가]는 ‘거짓·가짜’, 名[명]은 ‘이름’과 관련돼요.` 같은 글자가 반복되어도 독음을 생략하지 않는다. 조회용 `hanja`와 `components`에는 독음을 붙이지 않는다.

한국어 `semantic_hint`는 학습자에게 설명하는 친근한 해요체로 쓰고, 온점으로 끝나는 각 문장을 `-요.`로 맺는다. 명사로 풀이할 때는 받침에 맞춰 `이에요`와 `예요`를 구분하고, 동작이나 관계는 `뜻해요`, `나타내요`, `관련돼요`처럼 자연스럽게 설명한다. `-다.`로 끝나는 한다체나 `...함.` 같은 메모체를 섞지 않는다. 영어 설명을 함께 적은 힌트에도 `/` 앞의 한국어 부분에 이 규칙을 적용한다.

실제 단어의 뜻과 글자 구성에 따른 설명을 구별한다. 여러 독음이 있는 글자는 문맥의 독음을 확인하고, 복잡한 어원을 근거 없이 구성 풀이로 만들지 않는다. 뜻별 ID와 단어별 예문·출처·검수 상태 필드는 후속 스키마 작업에서 설계한다.

## 그래프와 조회

내부 그래프에는 **단어 항목**과 **한자 글자**라는 두 종류의 노드가 있다. 단어에 쓰인 한자끼리 직접 연결하는 대신 단어와 그 구성 한자를 연결하는 이분 그래프다. 독음 레코드는 글자에 딸린 정보로 유지한다. 호환 형식인 한자 없는 항목에는 한자 연결을 만들지 않는다. 현재 사전에는 한자 성분이 있는 항목만 수록한다. 혼합어도 실제 한자 성분에만 연결한다.

- 단어의 같은 글자가 반복되면 구성 분해에 모든 위치를 보존하고, 한자별 역색인에는 그 단어를 한 번만 연결한다.
- 여러 독음을 가진 글자는 분해 결과에 모든 후보를 제공한다. 한글 음절만으로 독음을 자동 선택하거나 두음법칙을 추정하지 않는다.
- 같은 글자의 독음별 조회는 글자 기준으로 연결 단어를 공유한다.
- 연결 수는 단어별 서로 다른 구성 글자 수를 합한 값이다. 독음 레코드 수나 반복 글자 위치 수와 구분한다.
- 정확 일치 조회와 연결 단어 목록은 입력 파일의 순서를 유지한다.

### 조회 방식

| 조회 | 일치 기준 |
| --- | --- |
| 단어 정확 조회 | 한글 표기 또는 한자 표기 |
| 한자 정확 조회 | 글자, 한자 ID 또는 한글 독음 |
| 웹 전체 검색 | 단어·한자의 표기와 뜻, 한자 ID와 독음의 부분 일치; 정확히 일치한 표제어를 먼저 표시; 영문 대소문자 구분 없음 |
| 웹 소리 검색 | 한글·로마자 독음의 정확 일치; 단어의 해당 음절 위치가 실제 한자 성분인 경우만 반환; 고유어 부분·접미 요소는 제외 |

정확 일치 조회는 유니코드 원문을 비교한다. 이체자·호환 한자·두음법칙에 따른 별칭은 자동으로 만들지 않는다. 일치하는 결과가 없으면 빈 배열을 반환한다.

### 화면의 깊이 1 그래프

웹 화면은 내부 연결을 **한자 노드와 단어 연결선**으로 표시한다. 선택 단어의 모든 구성 한자를 시작점으로 삼아, 이 글자가 들어간 단어와 그 단어의 구성 한자를 포함한다. 새로 만난 이웃 글자의 다른 단어는 확장하지 않는다.

세 글자 이상인 단어는 하나의 단어 이름에 여러 한자를 연결한다. 원래 구성 순서는 단어 데이터에 보존한다. API의 조회 우선순위와 응답은 [개발 안내](DEVELOPMENT.md#http-api), 화면 조작은 [웹 앱 사용 안내](WEB_APP.md#연결-그래프-읽기)를 참조한다.

## 문맥 연습: `practice.json`

웹 앱 전용 JSON 객체이며 세 JSONL 파일을 읽은 뒤 별도로 검증한다.

| 최상위 필드 | 규칙 |
| --- | --- |
| `version` | 현재 허용 값 `1` |
| `source` | 비어 있지 않은 출처 문자열 |
| `review_status` | 현재 허용 값 `draft` |
| `questions` | 비어 있지 않은 문항 배열 |

각 문항의 필드는 다음과 같다.

| 필드 | 규칙 |
| --- | --- |
| `id` | 비어 있지 않은 고유 문항 ID |
| `difficulty` | `easy`(기본), `medium`(응용), `hard`(심화) 중 하나 |
| `prompt_ko`, `prompt_en` | 비어 있지 않은 한국어·영어 문항 문자열 |
| `explanation_ko`, `explanation_en` | 비어 있지 않은 한국어·영어 해설 문자열 |
| `options` | 서로 다른 한글 표기를 가진 단어 참조 2–4개; 공백을 제외한 한글 표기가 중복되면 오류 |
| `answer` | 선택지에 포함된 단어 참조 하나 |

단어 참조는 `{ "word": "가명", "hanja": "假名" }`처럼 기존 단어의 한글·한자 쌍을 지정한다. 해설에는 위의 독음 병기 규칙을 적용하고, 정답·선택지의 `hanja`는 조회용 원문을 유지한다.

문맥 연습의 선택지는 한글 단어로 표시한다. 같은 한글 표기에 한자만 다른 동음이의어를 함께 제시하거나, 한자 표기 자체를 묻는 문항은 만들지 않는다. 문장의 상황·의미 단서로 답을 고르게 하고, 한자 구성은 정답 확인 뒤 해설에서 참고하도록 한다.

현재 예문과 해설은 프로젝트에서 직접 작성한 초안이다. 문항을 늘릴 때는 기존 정답 단어를 제외한 어휘에서 100개를 중복 없이 무작위 추출하고, 단어마다 한국어 문맥 예문·영어 번역·선택지·한영 해설을 작성한다. 추출 시드와 묶음은 데이터 작업 기록에 남긴다.

난이도는 문항의 어휘·선택지·문맥을 검토한 학습용 초기 분류다. 일상 어휘와 명확한 단서는 `easy`, 추상적인 의미와 관련 어휘 비교는 `medium`, 고전·전문 어휘나 세밀한 의미 구분은 `hard`로 분류한다. `normal` 어휘에도 심화 문항이 있으며 어휘 분류와 난이도를 같은 것으로 취급하지 않는다. 새 문항에는 반드시 난이도를 지정한다.

API는 전체 문항과 정답·해설을 제공하며, 각 문항의 `word_level`은 로더가 정답의 `(word, hanja)`로 조회한 `level`에서 채워 넣는다. 원본 `practice.json`에 어휘 분류를 중복 저장하지 않는다. 브라우저는 선택한 난이도·어휘 분류로 먼저 거른 뒤 연습 시작·재시작마다 문항을 섞어 앞의 10개를 뽑고 선택지 순서도 섞는다. 회차 안에서는 문항이 중복되지 않고, 회차 사이에는 재출제될 수 있다. 필터 결과가 10개 미만이면 해당 문항을 모두 사용하고, 0개이면 시작을 막는다. 채점과 완료 결과는 선택한 문항만을 기준으로 한다.

## 검증 범위

JSONL 로더는 필수 필드, ID·단어 중복, 음 그룹·한자 참조와 구성 순서를 검사한다. 오류에는 파일명과 실제 줄 번호를 포함하며, 실패하면 일부 데이터만으로 그래프를 반환하지 않는다.

연습 로더는 허용 버전·검수 상태, 문항 텍스트·난이도, 중복 ID, 선택지의 한글 표기 중복·정답과 단어 참조를 검사한다. 오류에는 파일명과 해당 문항 ID를 표시한다.

저장소 테스트는 최소 연결 단어 수, 힌트의 독음 표기, 기초 어휘 원본 행의 수록·제외 대응 같은 추가 규칙도 점검한다. 검증 명령은 [개발 안내](DEVELOPMENT.md#검증)를 참조한다. 구조 검증과 별도로 훈음·번역·예문의 정확성과 학습 효과를 확인해야 한다.
